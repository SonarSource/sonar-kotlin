Why is this an issue?

The primary purpose of classes that implement indexed access operators is element access, as is the case for arrays, lists, or maps. When a class implements indexed access operators, they should be used as operators instead of calling them as functions, because this is the intention of the designer of the API.

What is the potential impact?

Readability and Understanding

This change makes it easier to understand what a function does, because the semantics of indexed access operators is evident to the reader, while for a function call, the reader would need to know what the called function does.

Java interop

Kotlin permits Java get methods with at least one parameter and set methods with at least two parameters to be invoked using indexed-access syntax. This applies even when their arguments are not indexes or keys, so a syntactically valid rewrite does not always express the method’s behavior clearly.

For Java APIs, this rule reports only selected calls to get and set methods that represent element access on well-known indexed or keyed containers, including Java List and Map implementations, NIO buffers, BitSet, atomic arrays, and Android sparse arrays. Calls on other Java APIs are not reported.

The following examples illustrate this distinction:

import java.nio.ByteBuffer
import java.util.BitSet
import java.util.concurrent.CompletableFuture
import java.util.concurrent.TimeUnit

fun accessJavaApis(
    buffer: ByteBuffer,
    destination: ByteArray,
    bitSet: BitSet,
    future: CompletableFuture<String>,
) {
    buffer.get(0) // Noncompliant: single-element access
    buffer.get(destination) // Compliant: bulk read

    bitSet.get(5) // Noncompliant: single-bit access
    bitSet.get(1, 4) // Compliant: range operation

    future.get(1, TimeUnit.SECONDS) // Compliant: waits for a result with a timeout
}

How to fix it

Replace instance.get(index) with instance[index].

Replace instance.set(index, value) with instance[index] = value.

This also works with multi-index access operators.

Code examples

Noncompliant code example

interface Grid {
    operator fun get(row: Int, column: Int): Int
    operator fun set(row: Int, column: Int, value: Int)
}

fun indexedAccess(list: MutableList<Int>, map: MutableMap<String, Int>, grid: Grid) {
    list.get(1) // Noncompliant
    list.set(1, 42) // Noncompliant
    map.get("b") // Noncompliant
    map.set("b", 42) // Noncompliant
    grid.get(1, 2) // Noncompliant
    grid.set(1, 2, 42) // Noncompliant
}

Compliant solution

fun indexedAccess(list: MutableList<Int>, map: MutableMap<String, Int>, grid: Grid) {
    list[1] // Compliant
    list[1] = 42 // Compliant
    map["b"] // Compliant
    map["b"] = 42 // Compliant
    grid[1, 2] // Compliant
    grid[1, 2] = 42 // Compliant
    list.getOrNull(2) // Compliant, because function is not an operator
    list.getOrElse(3) {42} // Compliant, because function is not an operator
    map.getValue("a") // Compliant, because function is not an operator
    map.getOrElse("c") {42} // Compliant, because function is not an operator
}
