Why is this an issue?

Shared naming conventions allow teams to collaborate efficiently.

This rule raises an issue when a function name does not match a provided regular expression.

For example, with the default provided regular expression ^[a-zA-Z][a-zA-Z0-9]*$, the function:

fun _DoSomething() {...} // Noncompliant

should be renamed to

fun DoSomething() {...}

Exceptions

The following functions are not checked by this rule:

  • External functions (declared with the external modifier): the name is owned by the native ABI and cannot be changed without breaking interoperability.
  • Override functions (declared with the override modifier): the name is dictated by the supertype contract and cannot be changed without breaking the override.
  • Backtick-named test functions: functions annotated with @Test, @ParameterizedTest, or @RepeatedTest may use backtick names with spaces to express human-readable test descriptions.

For functions annotated with @Composable, the Jetpack Compose API guidelines take precedence over the configured format when the name already violates it:

  • Public and protected @Composable functions returning Unit must follow PascalCase (UI component convention).
  • Private and internal @Composable functions returning Unit may use either PascalCase or camelCase.
  • @Composable functions returning a non-Unit value must follow camelCase (composable factory convention).
  • @Composable functions annotated with @Preview may use backtick names as human-readable labels in the Android Studio preview panel.

If a @Composable function’s name already satisfies the configured format, it is always compliant regardless of return type or visibility.
